What I built

I built and deployed the workspace end to end: the FastAPI backend, model-provider routing, OAuth sign-in, credit-metered access, and the path from an idea to a structured build package.

The product moves through Spec → Plan → Harness → Tasks, with a human review before the next stage. The resulting tasks carry the context an engineer or coding agent needs to continue.

The problem

A promising idea can conceal different assumptions about users, requirements, and what “done” means. Passing that ambiguity straight into implementation makes the handoff harder to review.

The product makes those decisions visible before execution: what is needed, how it could be built, how it will be checked, and which tasks follow.

A consequential decision

I put validation assets before implementation tasks. That makes checking the proposed behavior part of the build package.

The tradeoff is an additional review step before execution. In return, the next stage receives explicit acceptance criteria and a way to check them.

The system around the model

Requests can route across Anthropic, OpenAI, and Google. OAuth handles sign-in, and users can use starter credits or bring their own provider credentials.

I built the handoff around reviewed artifacts rather than a single long response. Each task stays linked to the requirements it is intended to satisfy.

What is working

Thought2Build is fully working and deployed live. Visitors can open the product and start a workspace.

SPEC.md01 / 04

Make “done” explicit.

# Onboarding checklist

REQ-01  A signed-in user can complete a checklist item.
AC-01   Completion is still visible after a page refresh.

Boundary: users can update only their own checklist.
Review: confirm the checklist and acceptance criteria.

A requirement and an acceptance criterion give the build a concrete target.

PLAN.md02 / 04

Choose a path before implementing.

# One implementation approach

Store completion against (user_id, item_id).
PATCH /checklist/items/{id} accepts a completed flag.
The server verifies ownership before persisting it.

Decision: saved server state is authoritative.
Risk to check: an update must not affect another user.

The plan makes the persistence and authorization decisions explicit.

ACCEPTANCE.md03 / 04

Check the promised behavior.

# Acceptance check: AC-01 → REQ-01

Given: a signed-in user with an incomplete item
When:  they complete it and refresh the page
Then:  the same item remains complete

Boundary check:
A different user cannot update that checklist item.

The acceptance check tests both the promised behavior and its access boundary.

TASKS.md04 / 04

Hand off traceable work.

# Delivery task T-03 → REQ-01 / AC-01

Implement the checklist completion endpoint.
- Verify checklist ownership.
- Persist completion for the current user.
- Add the AC-01 acceptance check.

Done: completion survives refresh and the check passes.

A task points back to its requirement and check, so the next person has context.
